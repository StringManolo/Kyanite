# Релизы

Kyanite публикует архивы корневой файловой системы для каждой поддерживаемой архитектуры через GitHub Releases.

## Теги версий

Теги релизов имеют формат `vX.Y.Z`. Например:

```sh
git tag -a v0.1.0 -m "Kyanite 0.1.0"
git push origin v0.1.0
```

Отправка тега такого вида запускает workflow выпуска. Другие форматы тегов механизм автоматического обновления базы не использует.

## Файлы релиза

Каждый релиз содержит следующие файлы для каждой архитектуры:

- `kyanite-rootfs-<архитектура>.tar.xz`
- `kyanite-rootfs-<архитектура>.tar.xz.sha256`
- `kyanite-rootfs-<архитектура>.tar.xz.sha256.sig`

Файл `.sig` содержит подпись Ed25519 файла `.sha256`.

## Ключ подписи

Публичный ключ релизов хранится в:

```text
rootfs-overlay/etc/kpkg/kyanite-release.pub
```

Соответствующий закрытый ключ хранится как секрет репозитория GitHub:

```text
KYANITE_SIGNING_KEY
```

Никогда не добавляйте закрытый ключ подписи в репозиторий и не публикуйте его.

О проверке на стороне пользователя см. [Проверка релизов](../../SECURITY.md#verifying-releases) (на английском).

## Changelog

Если релизу требуется операция, которую нельзя выразить обычным обновлением файлов (например, замена предустановленного пакета), добавьте раздел для новой версии в:

```text
rootfs-overlay/usr/share/kyanite/CHANGELOG
```

Changelog описывает операции, которые программа обновления может выполнять при таких переходах.

## Сборки для разработки

Сборки из коммитов вне тега релиза получают метку на основе `git describe`, например:

```text
v0.1.0-3-g1a2b3c4
```

Сборки для разработки не подходят для автоматических обновлений базы. Программа обновления учитывает только теги релизов `vX.Y.Z`.
